## 2. Server-side session helper — `src/lib/session.ts`

- `export type Session = { userId: number; name: string }`.
- `getSession(): Promise&lt;Session | null&gt;` (105-109) — reads+verifies the signed httpOnly cookie, returns `null` if absent/invalid/expired. Safe in Server Components.
- `requireSession(redirectTo = "/login"): Promise&lt;Session&gt;` (115-119) — calls `getSession`, `redirect(redirectTo)` if null, otherwise returns it. **This is the pattern for every protected page.**
- `createSession` / `destroySession` — cookie writers, Server Actions/Route Handlers only.
- Doc comment (19-23) is explicit: "`getSession()` is the ONLY function anywhere in this app that may produce a user id to act on... never from a client-supplied id."

Usage examples: `src/app/account/page.tsx:20` — `const session = await requireSession("/login?next=/account")`, then queries `users` filtered by `session.userId`. `src/app/actions/checkout.ts:41,71,116` — `requireSession("/login?next=/checkout")` inside Server Actions. `src/lib/cart.ts:64,120` and `src/app/actions/reviews.ts:15`/`wishlist.ts:16` use the non-redirecting `getSession()` and return a `{ error }` state instead when signed out.

## 3. Ownership-checked query pattern

Canonical example, `src/app/actions/checkout.ts:72-77` (also confirmation page):
```ts
const [order] = await db
  .select({ ... })
  .from(schema.orders)
  .where(and(eq(schema.orders.id, orderId), eq(schema.orders.userId, session.userId)))
  .limit(1);
if (!order || order.status !== "pending") return { error: "Checkout not found." };
```
Same shape in `src/app/checkout/confirmation/page.tsx:17-18`, but calling `notFound()` instead of returning an error — that's the 404 pattern for a page route: `.where(and(eq(schema.orders.id, orderId), eq(schema.orders.userId, session.userId)))`, then `if (!order) notFound();`.

For tables keyed by `userId` directly (wishlist, reviews), the pattern is the same `and(eq(table.userId, session.userId), eq(table.xId, …))` filter baked into the query itself — see `src/app/actions/wishlist.ts:23` and `:46`. For cart (no direct `userId` column on `cart_items`), ownership goes through `findCartId()`/`resolveCart()` (`src/lib/cart.ts`) which resolve to the session's cart id, then every mutation also re-filters by that `cartId` in the `WHERE` (e.g. `src/app/actions/cart.ts:85-95`'s `ownedCartItem` helper, and the delete/update statements at lines 118, 136). Nowhere does any mutation trust an id from `formData` alone — it's always combined with a session-derived id in the same `WHERE`/`AND`.

CLAUDE.md itself states this rule under "Security" (lines 38-46): confirm from the session that a row is *this* user's row, filter by session user id in the query itself, and a resource belonging to another user returns 404 (never a different error that leaks existence).

## 4. Server Actions conventions — `src/app/actions/*.ts`

Files: `auth.ts`, `cart.ts`, `checkout.ts`, `reviews.ts`, `wishlist.ts` (flat, one file per domain, not nested).

- `"use server";` is the first line of the file (module-level directive), e.g. `cart.ts:1`, `reviews.ts:1`, `wishlist.ts:1`, `checkout.ts:1`, `auth.ts:1`.
- A per-domain exported state type: `CartActionState`, `ReviewActionState`, `WishlistActionState`, `AddressActionState`, `AuthFormState` — always a union `{ error: string } | &lt;success shape&gt; | null`, matching `useActionState`'s `(prevState, formData)` signature (first param usually named `_prev`/`_previous`).
- Validation is manual, inline, server-side: `Number(formData.get(...))`, `Number.isInteger(...)` checks, length caps on strings, returning `{ error: "..." }` on any failure — never a thrown exception for user-facing validation.
- Ownership/auth check happens first thing inside the action (`getSession()`/`requireSession()`), before touching `formData` business logic in some files, or right after parsing in others — both orders are present, but the auth check always happens before any DB write.
- After a mutation, `revalidatePath(...)` is called explicitly — e.g. `revalidatePath("/", "layout")` when the header cart count needs refreshing (`cart.ts:80`, `wishlist.ts:58`), plus the specific page (`revalidatePath("/cart")`, `revalidatePath("/wishlist")`, `revalidatePath(\`/product/${product.slug}\`)` in `reviews.ts:31`).
- `redirect(...)` is used instead of returning state when the action's job is to navigate on success (e.g. `checkout.ts:66` `redirect(`/checkout/payment?order=${order.id}`)`, and every `auth.ts` action).
- No generic try/catch wrapper pattern — errors are prevented by validating first; unexpected DB errors are left to bubble to `error.tsx`.
